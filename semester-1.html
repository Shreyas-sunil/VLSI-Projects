MVE311TB-P1Mini Graph-Based STA Engine Validated Against OpenSTA Track CIntermediateBuild first 4-6 wk22/30

Identification

Static Timing Analysis with TCL Scripting (MVE311TB), Semester 1. Level: Foundational. Primary track C; secondary: A. Estimated effort: 4-6 weeks (about 48-72 focused hours at roughly 12 h/week). Carried over from the 2024 card MVE311TA-P1.

Syllabus mapping: Units I, II, IV, V: timing arcs, NLDM delay tables, slew propagation, setup/hold, slack and a subset of SDC

Engineering problem

Students use STA as a black box, so slack numbers are never questioned. Writing a small engine exposes how arrival times, required times and slew degradation are computed and where tool results can differ.

Proposed solution and architecture

Parse a gate-level Verilog netlist and a Liberty subset (NLDM tables with interpolation), build a timing graph, propagate arrival and slew in topological order, run backward required-time propagation, then report setup and hold slack. Support create_clock, set_input_delay, set_output_delay. Correlate every endpoint against OpenSTA on the same netlist and library.

Netlist + Liberty parser→Timing graph builder→Arrival/slew propagation→Required-time propagation→Slack report→OpenSTA correlation script

Implementation plan

  1. Study: Bhasker/Chadha ch. 1-4 and the Liberty NLDM format. Build: parser and graph for a 20-gate netlist. Artifact: graph dump. Gate: hand-checked arrival times match.
  2. Build: slew-aware delay lookup with bilinear interpolation. Test: compare a single cell delay with the Liberty table by hand. Gate: error below table interpolation tolerance.
  3. Build: setup/hold checks for flip-flops using library constraint tables plus clock skew. Artifact: report with slack per endpoint. Gate: matches a hand calculation on a 3-stage pipeline.
  4. Verify: run on 5 netlists synthesised by Yosys with the sky130 library and compare to OpenSTA. Artifact: correlation CSV. Gate: all endpoints reported, error statistics documented.
  5. Document: list the features not supported (wire models, CRPR, derates) and where your results diverge from OpenSTA, with reasons.

Tools and resources

Python or C++, OpenSTA (open source), Yosys, SkyWater sky130 Liberty files. No commercial EDA needed. No hardware needed.

Measurable evaluation

  • Baseline: OpenSTA run with ideal wires on the same netlists and library.
  • Measure: Per-endpoint arrival and slack difference in ps; fraction of endpoints within 1 percent; runtime.
  • Success looks like: Documented agreement on a stated set of netlists, with each residual difference explained. Do not claim equivalence with a signoff tool.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

Source, 5 test netlists, correlation CSV, short design note, README.

Career value

Competencies: Timing graph algorithms, Liberty modelling, delay calculation, tool correlation.

Resume bullet (use only after you build it and fill in measured numbers): Implemented a graph-based static timing analyzer with NLDM delay and slew propagation and correlated endpoint slack against OpenSTA on N netlists (report the measured error).

Likely interview questions:

  • Why does slew degrade along a wire and how does it change the next gate delay?
  • What is the difference between graph-based and path-based analysis?
  • How are hold checks affected by clock skew?
  • Where would your engine diverge from signoff STA?

Risks and fallback

Liberty parsing is fiddly; start with one library and one corner. Do not attempt crosstalk or OCV here.

Extensions

  • Add a simple Elmore wire-delay model
  • Add multicycle and false path support
  • Expose the engine through a small Tcl command shell (get_timing_paths style)

MVE311TB-P2SDC and Tcl-Driven Timing Closure of an INT8 MAC Array Track AIntermediateBuild next 5-7 wk24/30

Identification

Static Timing Analysis with TCL Scripting (MVE311TB), Semester 1. Level: Industry-oriented. Primary track A; secondary: C. Estimated effort: 5-7 weeks (about 60-84 focused hours at roughly 12 h/week). Carried over from the 2024 card MVE311TA-P2.

Syllabus mapping: Units IV, V: SDC constraints and exceptions, Tcl path tracing and report analysis, violation fixing; also Practicals 10-11 (synthesis and STA) of MVE212IA

Engineering problem

A systolic MAC array is the core of every AI accelerator, and its critical path decides the clock. The question is how far constraints, pipelining and retiming can push frequency before area and power rise unacceptably.

Proposed solution and architecture

Build a parameterised INT8 MAC array in Verilog, write clock and I/O constraints, synthesise and place it with OpenROAD, then iterate: inspect the worst paths, add pipeline stages, and apply multicycle or false-path exceptions only where they are architecturally justified. Drive all analysis from OpenSTA/OpenROAD Tcl scripts (path groups, filtered reports, a small Tcl utility that ranks failing endpoints by cause). Document each change and its slack effect.

MAC array RTL (parametric)→SDC constraints→Yosys synthesis→OpenROAD place + STA→Tcl report scripts→Violation triage→Pipeline/retime changes

Implementation plan

  1. Study: setup/hold, clock uncertainty, SDC semantics, basic Tcl (Welch et al.). Build: 4x4 and 8x8 array RTL. Artifact: RTL + testbench. Gate: array matches a NumPy matmul reference.
  2. Build: SDC with clocks, uncertainty, input and output delays. Gate: no unconstrained endpoints in the report.
  3. Baseline: synthesise and run STA at a stressed clock from a Tcl script that writes WNS/TNS and the top 20 paths to CSV. Gate: reproducible via one script.
  4. Optimise: apply pipeline insertion and operand registering. For each change record WNS, TNS, area. Gate: documented monotonic improvement or an explanation.
  5. Check: write a Tcl path-tracing utility that shows every exception is legitimate (no hidden bugs). Benchmark: frequency vs area Pareto. Document.

Tools and resources

Yosys, OpenROAD/OpenSTA or OpenLane, sky130 or NanGate45 PDK, Verilator for functional check. Optional: commercial PrimeTime/Genus (not needed).

Measurable evaluation

  • Baseline: Unpipelined 8x8 array at a fixed target clock.
  • Measure: WNS, TNS, number of failing endpoints, area, achieved frequency, power estimate.
  • Success looks like: A documented Pareto of frequency vs area with explanations for each step. Results are post-synthesis or post-placement, not silicon.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

RTL, SDC, scripts, reports for each iteration, Pareto plot, 2-page note.

Career value

Competencies: Timing closure workflow, constraint writing, Tcl scripting for STA, microarchitecture timing trade-offs.

Resume bullet (use only after you build it and fill in measured numbers): Closed timing on a parameterised INT8 MAC array in OpenROAD, improving WNS from X to Y with pipelining while tracking area (use your measured numbers).

Likely interview questions:

  • Why did you choose this pipeline cut?
  • When is a multicycle path legitimate?
  • How does clock uncertainty change the result?
  • How does your Tcl script trace a path back to its cause?

Risks and fallback

Over-constraining or using false paths to hide failures. Fallback: reduce array size and clock target.

Extensions

  • Sweep array sizes 4,8,16
  • Compare ripple vs carry-save accumulation

MVE311TB-P3Slack Prediction from Pre-Route Features: A Variation-Aware Timing Study Track CResearch-gradeStretch 8-12 wk25/30

Identification

Static Timing Analysis with TCL Scripting (MVE311TB), Semester 1. Level: Advanced / research. Primary track C; secondary: A. Estimated effort: 8-12 weeks (about 96-144 focused hours at roughly 12 h/week). Carried over from the 2024 card MVE311TA-P3.

Syllabus mapping: Units II, III, V: parasitics, crosstalk, variability, post-route timing vs earlier estimates; Tcl report extraction

Engineering problem

Late timing surprises cost design iterations. The hypothesis to test is whether features available before routing (fanout, estimated wire length, cell type, logic depth) can predict post-route slack well enough to guide early optimisation.

Proposed solution and architecture

Generate a dataset by running many OpenROAD flows over several open designs with varied constraints and utilisation. Extract endpoint features pre-route and slack post-route. Train simple models (linear, gradient-boosted trees) and compare to the estimate OpenROAD already gives pre-route. Report where models fail (crosstalk, long wires).

Design/constraint sweeper→OpenROAD flow runner→Feature extractor→Dataset store→Model training + eval→Error analysis

Implementation plan

  1. Study: parasitics, crosstalk delta delay, existing pre-route slack prediction literature. Gate: you can state what is already known.
  2. Build: automated flow runner producing reports for 5+ designs and 20+ configurations. Artifact: raw reports. Gate: runs unattended.
  3. Build: feature extraction and a leakage-free train/test split by design. Gate: test designs unseen in training.
  4. Train: baseline linear and tree models; compare with OpenROAD pre-route estimate. Gate: metrics table with confidence intervals.
  5. Analyse: failure cases; ablate features. Document honestly, including negative results.

Tools and resources

OpenROAD-flow-scripts, Tcl for report extraction, Python, scikit-learn, sky130/NanGate45. CPU only. Related work exists (for example Guo et al., DAC 2022 on pre-routing slack prediction), so novelty is student-level unless you add a new angle.

Measurable evaluation

  • Baseline: OpenROAD pre-route slack estimate.
  • Measure: MAE and R2 of endpoint slack in ps; rank correlation; error on worst 5 percent endpoints.
  • Success looks like: Any honest, reproducible comparison; a publishable angle exists only if you add a distinct contribution (new feature class or cross-design generalisation).

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

Dataset generator, trained models, report, paper-style draft, reproducible repo.

Career value

Competencies: Data pipeline for EDA, ML evaluation discipline, timing physics intuition.

Resume bullet (use only after you build it and fill in measured numbers): Built an automated OpenROAD dataset pipeline and evaluated pre-route slack predictors on unseen designs (state measured error).

Likely interview questions:

  • How did you avoid train/test leakage?
  • Which features mattered most and why physically?
  • Why does crosstalk hurt prediction?
  • What would you need to deploy this in a flow?

Risks and fallback

Few designs cause overfitting; keep scope modest. Fallback: study a single design family and report limits.

Extensions

  • Graph neural network variant
  • Predict congestion alongside slack

MVE212IA-P1Multiplier Architecture Shootout for INT8 MAC Energy Track AIntermediateBuild first 4-6 wk22/30

Identification

Low Power Digital IC Design (MVE212IA), Semester 1. Level: Foundational. Primary track A; secondary: C. Estimated effort: 4-6 weeks (about 48-72 focused hours at roughly 12 h/week).

Syllabus mapping: Unit II arithmetic building blocks and adders; Practicals 6 (adder delay and power), 10 (synthesis with area, power and timing reports) and 12 (LEC)

Engineering problem

The multiplier dominates MAC energy. Which INT8 multiplier (array, Baugh-Wooley, radix-4 Booth) is actually lowest energy per operation on realistic data, rather than random inputs?

Proposed solution and architecture

Implement array, Baugh-Wooley and radix-4 Booth multipliers with a shared accumulate stage. Drive them with random data and with real quantised CNN activations and weights. Estimate dynamic power from gate-level switching activity (VCD/SAIF) with OpenSTA power analysis.

Three multiplier RTLs→Common MAC wrapper→Data generators (random, CNN)→Gate-level sim→Switching-activity power estimate→Comparison report

Implementation plan

  1. Study: Booth encoding, partial product reduction. Build: three multipliers. Gate: exhaustive 8x8 test passes.
  2. Build: MAC wrapper and test vectors from a quantised CNN. Gate: vectors reproducible from a script.
  3. Synthesise with Yosys to sky130; record area and delay. Gate: no timing violations at the chosen clock.
  4. Simulate gate-level with real activity; extract VCD; run OpenSTA power. Gate: power numbers repeatable.
  5. Analyse: energy per MAC under both data sets; document that estimates are pre-layout activity-based, not silicon.

Tools and resources

Icarus/Verilator, Yosys, OpenSTA, sky130 Liberty, Python/NumPy, PyTorch for activation capture (CPU is enough).

Measurable evaluation

  • Baseline: Plain synthesised `*` operator from Yosys.
  • Measure: Area, critical delay, estimated dynamic power, energy per MAC for random vs CNN data.
  • Success looks like: A table with clear caveats showing which multiplier wins at which clock and data distribution.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

RTL, testbenches, scripts, result tables, short report.

Career value

Competencies: Arithmetic architecture, switching-activity power estimation.

Resume bullet (use only after you build it and fill in measured numbers): Compared three INT8 multiplier architectures on gate-level switching activity from real CNN data (report measured energy/MAC).

Likely interview questions:

  • Why is power data-dependent?
  • What does Booth recoding save and cost?
  • Why can random data mislead?
  • How accurate is vectorless power estimation?

Risks and fallback

Synthesis may flatten differences; check netlist structure. Fallback: use post-synthesis counts of cells only.

Extensions

  • Add approximate multipliers and measure accuracy loss
  • Add INT4 variants

MVE212IA-P2Zero-Skipping and Clock-Gated PE Array: Measured Energy on Sparse Activations Track AAdvancedBuild next 6-8 wk25/30

Identification

Low Power Digital IC Design (MVE212IA), Semester 1. Level: Industry-oriented. Primary track A; secondary: C. Estimated effort: 6-8 weeks (about 72-96 focused hours at roughly 12 h/week).

Syllabus mapping: Units III, V: signal gating, switching-activity reduction, architecture-level power; Practicals 7 (master-slave DFF), 9 (code coverage) and 10 (synthesis reports)

Engineering problem

Post-ReLU activations are often sparse. Gating idle processing elements should save dynamic power, but gating logic itself costs area and can hurt timing.

Proposed solution and architecture

Build a baseline PE array and a variant with operand isolation, enable-based clock gating (using library ICG cells) and zero detection. Quantify energy per inference layer using real sparse feature maps from a small quantised CNN.

PE (baseline)→PE (gated)→Zero detector→Array controller→Activity-based power flow→Sparsity sweep

Implementation plan

  1. Study: clock gating, glitch power, ICG cells. Gate: you can draw a safe gating enable timing diagram.
  2. Build baseline array and verify against reference. Gate: bit-exact.
  3. Build gated variant; add assertions that gating never drops valid data. Gate: random + directed tests pass.
  4. Measure: power vs sparsity (0 to 90 percent) using VCD activity. Gate: curves reproducible.
  5. Check: area and timing cost of gating; compute break-even sparsity. Document.

Tools and resources

Verilator, Yosys, OpenSTA/OpenROAD (CTS handles gated clocks), sky130, SymbiYosys optional for the gating assertion.

Measurable evaluation

  • Baseline: Baseline array without gating on the same data.
  • Measure: Dynamic power, energy per layer, break-even sparsity, area overhead, WNS impact.
  • Success looks like: Break-even sparsity identified with the measurement conditions stated; no claim beyond the tested networks.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

RTL, assertions, scripts, plots, report.

Career value

Competencies: Power-aware microarchitecture, clock gating, power measurement discipline.

Resume bullet (use only after you build it and fill in measured numbers): Implemented zero-skipping/clock-gated PE array and measured energy vs activation sparsity on real CNN feature maps.

Likely interview questions:

  • How do you avoid clock glitches with gating?
  • Why does gating affect CTS?
  • What breaks the savings?
  • How does sparsity vary by layer?

Risks and fallback

Gated clocks complicate STA and CTS; keep enables registered. Fallback: use operand isolation only.

Extensions

  • Structured sparsity (N:M)
  • Compare with data-gating of multiplier inputs only

MVE212IA-P3Voltage-Parallelism-Frequency Trade-offs for an Accelerator: Calibrated Energy Model Track AResearch-gradeStretch 8-10 wk23/30

Identification

Low Power Digital IC Design (MVE212IA), Semester 1. Level: Advanced / research. Primary track A; secondary: C. Estimated effort: 8-10 weeks (about 96-120 focused hours at roughly 12 h/week).

Syllabus mapping: Unit V parallel architecture with voltage reduction, power and performance management; Unit I power components; Practical 5 (PVT variation)

Engineering problem

Doubling parallelism and lowering voltage can cut energy per operation, but leakage, memory and interconnect limit the gain. Where is the optimum for a MAC array under realistic constraints?

Proposed solution and architecture

Characterise a MAC cell across sky130 corners and supply voltages in ngspice, calibrate an analytical energy/delay model, and combine with a cycle-accurate array simulator to find energy-delay-optimal parallelism per layer. Include a power-gating overhead model; state clearly that UPF-driven power-gating verification is not fully supported by the open flow.

SPICE characterisation→Calibrated energy/delay model→Array simulator→Optimiser→Sensitivity analysis

Implementation plan

  1. Study: alpha-power law, leakage, DVFS theory. Gate: you can derive E ~ CV^2 scaling.
  2. Build: ngspice testbenches for a representative critical path across corners. Artifact: delay/energy tables.
  3. Fit: model vs SPICE with error bars. Gate: error documented.
  4. Build: array simulator and optimiser over parallelism and voltage. Gate: reproduces model for a single configuration.
  5. Validate: sensitivity to leakage and memory energy assumptions; document limits.

Tools and resources

ngspice, sky130 models, Python. Fully software; no hardware needed. Related prior work on voltage/parallelism trade-offs is classical, so the novelty is the calibrated accelerator case study.

Measurable evaluation

  • Baseline: Fixed-voltage, fixed-parallelism design.
  • Measure: Energy per MAC, throughput, energy-delay product across (V, parallelism).
  • Success looks like: A calibrated model with stated validity range, plus recommendations. Intended targets, not silicon measurements.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

Model code, SPICE decks, plots, paper-style write-up.

Career value

Competencies: Quantitative power modelling, SPICE characterisation, design-space optimisation.

Resume bullet (use only after you build it and fill in measured numbers): Built a SPICE-calibrated energy-delay model for a MAC array and optimised voltage/parallelism (report fit error).

Likely interview questions:

  • Where does the model break near threshold?
  • How is leakage modelled?
  • Why is memory not scaled the same way?
  • How would DVFS granularity change the result?

Risks and fallback

SPICE characterisation scope can explode; limit to one critical path. Fallback: use published scaling laws as stated assumptions.

Extensions

  • Add SRAM retention voltage limits
  • Per-layer DVFS schedule

MVE213IA-P1Boot-to-Driver Firmware Stack from Reset Vector Track BIntermediateBuild first 4-6 wk19/30

Identification

Advanced Embedded System Design (MVE213IA), Semester 1. Level: Foundational. Primary track B; secondary: C. Estimated effort: 4-6 weeks (about 48-72 focused hours at roughly 12 h/week). Carried over from the 2024 card MVE313IA-P1.

Syllabus mapping: Unit IV linker scripts, ELF, bootloaders, BSP and HAL; Unit III memory-mapped I/O, UART and SPI; Experiments 1-4 and 6

Engineering problem

Most students call vendor HAL functions without understanding startup code, linker scripts and register-level drivers. Firmware and driver roles require exactly that understanding.

Proposed solution and architecture

On a Cortex-M or RISC-V target (hardware or QEMU/Renode), write the reset handler, vector table, linker script, .data/.bss init, and register-level GPIO, UART, SysTick and I2C drivers with unit tests that run on the emulator.

Startup + vector table→Linker script→Register-level drivers→Test harness (emulated)→Application

Implementation plan

  1. Study: ARM Cortex-M or RISC-V boot sequence, ELF, linker script syntax. Gate: can explain every section.
  2. Build: startup code and linker script for a blinky. Artifact: map file. Gate: runs on emulator.

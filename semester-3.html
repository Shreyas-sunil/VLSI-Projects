MVE231TA-P1UVM Agent, Sequences and Scoreboard for an AXI-Stream FIFO Track CIntermediateBuild first 4-6 wk22/30

Identification

Universal Verification Methodology (UVM) (MVE231TA), Semester 3. Level: Foundational. Primary track C; secondary: A. Estimated effort: 4-6 weeks (about 48-72 focused hours at roughly 12 h/week). New for the 2026 scheme.

Syllabus mapping: Units I-II: UVM base class library, testbench architecture, phases, TLM and reporting; sequences, sequencer, driver, monitor, configuration database and factory

Engineering problem

Class-based SystemVerilog testbenches work, but they are hard to reuse across projects and teams. UVM imposes a standard structure; the question is what it costs and what it gives back on a small, well-understood block.

Proposed solution and architecture

Port the constrained-random testbench of MVE222IA-P1 to UVM: an AXI-Stream agent (sequencer, driver, monitor) on each side, a reference model and scoreboard connected through TLM analysis ports, configuration through uvm_config_db, and factory overrides to swap sequences and inject errors. Run it on a UVM-capable simulator, or with pyuvm on cocotb if none is available, and compare effort and bugs found with the original testbench.

AXI-Stream agent (input)→AXI-Stream agent (output)→Sequence library→Reference model→Scoreboard (TLM)→Environment + tests→Factory overrides

Implementation plan

  1. Study: the UVM Primer chapters on components, phases and TLM. Build: a minimal environment with one agent and a smoke test. Gate: phases and reports behave as expected.
  2. Build: driver and monitor with randomised back-pressure on tready. Gate: the monitor reconstructs every transfer the driver sends.
  3. Build: reference model and scoreboard via analysis ports; sequences for bursts, gaps and full/empty corners. Gate: zero mismatches on the correct DUT.
  4. Inject bugs (off-by-one full flag, dropped beat) with DUT variants and factory-overridden sequences. Gate: each bug caught with a clear message.
  5. Compare with the plain SystemVerilog testbench: lines of code, time to add a new test, bugs found, simulation speed.

Tools and resources

Questa or Riviera-PRO through EDA Playground (free account) or a university licence for SystemVerilog UVM; alternatively pyuvm with cocotb on Verilator or Icarus (open source). State which one you used.

Measurable evaluation

  • Baseline: The class-based SystemVerilog testbench from MVE222IA-P1.
  • Measure: Functional coverage, bugs detected, effort to add a test, simulation time.
  • Success looks like: A working, reusable agent and environment with a documented comparison. pyuvm and SystemVerilog UVM differ; do not claim they are equivalent.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

UVM environment source, tests, coverage reports, comparison note.

Career value

Competencies: UVM architecture, TLM, sequences, factory and configuration database.

Resume bullet (use only after you build it and fill in measured numbers): Built a reusable UVM AXI-Stream agent and scoreboard that caught N injected FIFO bugs, and compared effort with a plain SystemVerilog testbench.

Likely interview questions:

  • Why separate the sequencer and the driver?
  • What does the factory let you change without editing code?
  • How do analysis ports decouple the scoreboard?
  • When do you raise and drop objections?

Risks and fallback

Access to a full UVM simulator. Fallback: pyuvm on cocotb, which is free.

Extensions

  • Add a functional coverage collector and a closure report
  • Reuse the agent in MVE231TA-P2

MVE231TA-P2RAL-Driven Verification of Accelerator CSRs with Coverage Closure Track CAdvancedBuild next 6-8 wk24/30

Identification

Universal Verification Methodology (UVM) (MVE231TA), Semester 3. Level: Industry-oriented. Primary track C; secondary: A. Estimated effort: 6-8 weeks (about 72-96 focused hours at roughly 12 h/week). New for the 2026 scheme.

Syllabus mapping: Unit III: coverage-driven verification, functional coverage, assertions, scoreboards, UVM register abstraction layer (mirroring, block configuration, adapters), coverage closure; Unit IV SoC and protocol verification

Engineering problem

Accelerator control registers are where software meets hardware. Bugs in access policies, reset values or side effects break drivers silently. A UVM register model generated from the register specification checks all of this systematically.

Proposed solution and architecture

Generate a UVM RAL model from the YAML register map of MIS325DM-P3 (or from SystemRDL with PeakRDL), connect it through an AXI-Lite adapter and predictor to the accelerator CSR block, and run the built-in register sequences (reset, bit-bash, access) plus custom sequences for side effects (start bits, write-1-to-clear status, interrupt masks). Write covergroups for fields and access combinations and close coverage with targeted sequences, documenting every exclusion.

Register spec (YAML or SystemRDL)→RAL generator→AXI-Lite agent + adapter→Predictor + mirror→Built-in register sequences→Side-effect sequences→Coverage model

Implementation plan

  1. Study: UVM RAL classes, front-door vs back-door access, predictors. Gate: the generated model compiles and matches the specification.
  2. Build: AXI-Lite agent and adapter; run uvm_reg_hw_reset_seq. Gate: every reset value checked.
  3. Run bit-bash and access sequences; add back-door paths for fast checks. Gate: any access-policy bugs logged and fixed.
  4. Add custom sequences for W1C status, self-clearing start bits and interrupt masking, with assertions. Gate: side-effect checks pass.
  5. Close coverage: field and cross coverage, targeted sequences, justified exclusions. Artifact: closure report.

Tools and resources

A SystemVerilog UVM simulator (Questa or Riviera through EDA Playground, or a licence); Python or PeakRDL for RAL generation. pyuvm's register layer is less complete, so use SystemVerilog UVM for this one if you can.

Measurable evaluation

  • Baseline: Hand-written directed CSR tests.
  • Measure: Register and field coverage, bugs found, time to regenerate after a specification change, regression runtime.
  • Success looks like: All registers verified against the specification with a coverage closure report and justified exclusions. A student IP, not a signed-off block.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

RAL generator, UVM environment, sequences, coverage database and report.

Career value

Competencies: UVM RAL, coverage closure, register specifications, HW/SW interface verification.

Resume bullet (use only after you build it and fill in measured numbers): Verified accelerator CSRs with a generated UVM RAL model, reaching X percent field coverage with documented exclusions (report your numbers).

Likely interview questions:

  • What does the RAL mirror represent?
  • When would you use back-door access?
  • How do you verify a write-1-to-clear field?
  • What makes a coverage exclusion justified?

Risks and fallback

Simulator access for full UVM. Fallback: run only the RAL part on EDA Playground.

Extensions

  • Generate C driver headers from the same specification and co-test with firmware
  • Add a DMA agent for end-to-end tests of MVE434P-P1

MVE231TA-P3ML-Guided Coverage Closure vs Constrained Random in UVM: A Controlled Study Track CResearch-gradeStretch 8-10 wk27/30

Identification

Universal Verification Methodology (UVM) (MVE231TA), Semester 3. Level: Advanced / research. Primary track C; secondary: A. Estimated effort: 8-10 weeks (about 96-120 focused hours at roughly 12 h/week). New for the 2026 scheme.

Syllabus mapping: Unit V: machine learning for verification engineers, AI-driven test generation, AI-assisted coverage closure, LLMs for UVM verification; Unit III coverage closure

Engineering problem

The last few percent of functional coverage consume a large part of a verification schedule. Published work suggests ML can steer stimulus towards uncovered bins, but results depend heavily on the design and the baseline. A controlled study on open designs tests whether it helps.

Proposed solution and architecture

Pick two open designs with non-trivial coverage models (for example an AXI crossbar and the decoder and hazard logic of an RV32 core). Build a UVM or pyuvm testbench that exposes sequence knobs (constraint weights, lengths, ordering). Compare plain constrained random, a coverage-feedback heuristic, Bayesian optimisation over the knobs, and an LLM that proposes sequences from the uncovered-bin report, each under the same simulation budget and repeated seeds.

Designs + coverage models→Knob-exposed sequences→Random baseline→Feedback heuristic→Bayesian optimiser→LLM sequence proposer→Statistics

Implementation plan

  1. Study: coverage-directed test generation and surveys of AI-assisted verification. Gate: related-work table and a clear hypothesis.
  2. Build testbenches and coverage models for both designs. Gate: random-baseline coverage curves over 10 seeds.
  3. Implement the feedback heuristic and Bayesian optimisation (Optuna or scikit-optimize). Gate: identical simulation budget per method.
  4. Implement the LLM proposer with strict validation (proposals must compile and respect constraints). Gate: invalid proposals counted, not silently dropped.
  5. Compare simulations needed to reach 90, 95 and 99 percent coverage with confidence intervals, and analyse which bins each method reaches and why.

Tools and resources

pyuvm and cocotb with Verilator, or SystemVerilog UVM on a licensed simulator; Python, Optuna or scikit-optimize; a local LLM. Open designs from OpenTitan or the PULP platform (check licences).

Measurable evaluation

  • Baseline: Constrained random with default weights and the same simulation budget.
  • Measure: Simulations and CPU time to each coverage target, final coverage, bins reached only by one method, variance across seeds.
  • Success looks like: A statistically fair comparison, with negative results reported if ML does not help. Claims limited to the tested designs.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

Testbenches, optimisers, run logs, analysis notebook, paper-style report.

Career value

Competencies: Coverage closure, ML for verification, experiment design, LLM evaluation.

Resume bullet (use only after you build it and fill in measured numbers): Compared Bayesian and LLM-guided stimulus with constrained random on two open designs; the best method reached 95 percent coverage in X percent fewer simulations (report your numbers).

Likely interview questions:

  • Why must every method get the same simulation budget?
  • Which bins stayed hard and why?
  • How do you stop an LLM from producing illegal stimulus?
  • What would make this result publishable?

Risks and fallback

If the coverage model is too easy every method looks the same; choose designs with genuinely hard bins. Fallback: one design.

Extensions

  • Add reinforcement learning over sequence ordering
  • Submit to a verification workshop such as DVCon India with an honest scope

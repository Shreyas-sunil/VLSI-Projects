Semester IV

You take 2 subjects this semester: 1 core plus 1 elective (one option from the group). 7 credits in total.

The page lists 5 entries because every elective option is shown, so you can compare them before choosing. Each entry has 3 project cards (15 cards in all). You only need the cards for the subjects you take.

Semester IV - the major project and research

Build these first: MVE442PA-P1MVE442PA-P2MVE442PA-P3MVE341EA-P1

Prerequisites: the minor-project accelerator, an RV32 core, a UVM environment, a literature map and a measurement database. The 18-week major project is individual and requires presenting or publishing the work.

Semester IV is only 7 credits on paper (major project 5 plus one 2-credit MOOC), but the major project is still 18 weeks of full-time work. Choose one major-project path and use the Group E MOOC as supporting study.

MVE442PA-P1Quantised Inference SoC: RISC-V Host + INT8 Systolic Engine + DMA, FPGA and PPA Track AResearch-gradeBuild first 18 wk27/30

Identification

Major Project (MVE442PA), Semester 4. Level: Foundational. Primary track A; secondary: C. Estimated effort: 18 weeks (about 216 focused hours at roughly 12 h/week). Carried over from the 2024 card MVE442P-P1.

Syllabus mapping: Guideline: gap analysis, individual implementation, mandatory presentation or publication

Engineering problem

Integration is the hard part: host, driver, DMA, accelerator and memory must work together and be measured against baselines.

Proposed solution and architecture

Integrate your RV32 core, the minor-project accelerator, DMA and scratchpads over AXI; software stack with driver and a compiler-like layer mapping a small CNN or transformer block; end-to-end inference, measured against CPU and GPU baselines.

RISC-V host→AXI interconnect→DMA→Accelerator→Driver→Model mapper→Benchmarks
FPGA note: board optional. RTL simulation plus synthesis reports is a valid path; results are then simulation and synthesis estimates, not on-board measurements.

Implementation plan

  1. Gap analysis and spec.
  2. Integration.
  3. Software stack.
  4. End-to-end model.
  5. Evaluation.
  6. Paper.

Tools and resources

Verilator, Yosys, OpenLane, FPGA optional, PyTorch, Timeloop optional.

Measurable evaluation

  • Baseline: CPU-only inference, accelerator without SoC.
  • Measure: End-to-end latency, throughput, energy proxy, area, accuracy.
  • Success looks like: Accurate end-to-end results with stated baselines.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

RTL, software, report, paper, demo.

Career value

Competencies: SoC integration, HW/SW co-design.

Resume bullet (use only after you build it and fill in measured numbers): Built an end-to-end RISC-V + INT8 accelerator SoC with measured latency, area and accuracy.

Likely interview questions:

MVE341EC-P1Logical-Effort Path Sizing Tool Calibrated and Verified Against ngspice in sky130 Track AIntermediateBuild first 3-5 wk22/30

Identification

CMOS Digital VLSI Design (MVE341EC), Semester 4. Level: Foundational. Primary track A; secondary: C. Estimated effort: 3-5 weeks (about 36-60 focused hours at roughly 12 h/week). New for the 2026 scheme.

Syllabus mapping: Weeks 3-5: combinational logic design and logical effort; Weeks 1-2: inverter, power and SPICE simulation

Engineering problem

Logical effort gives a quick estimate of the best gate sizes and number of stages, but its parameters must be calibrated for a real process. The project checks how good those estimates are in sky130.

Proposed solution and architecture

Characterise sky130 inverter, NAND2, NOR2 and a complex gate in ngspice to extract tau, parasitic delay p and logical effort g. Build a tool that, for a given path and load, computes the optimal number of stages and gate sizes, generates a sized SPICE netlist and compares predicted with simulated delay on decoders, a carry chain and a high-fanout buffer chain.

Gate characterisation→Parameter extraction (tau, p, g)→Path optimiser→Netlist generator→SPICE verification→Error analysis

Implementation plan

  1. Study: logical effort (Weste and Harris ch. 4). Build: FO4 inverter and gate characterisation in ngspice. Gate: extracted parameters with fitting error.
  2. Build: a path optimiser for N stages with branching. Gate: matches textbook examples.
  3. Generate sized netlists and simulate them. Gate: predicted vs simulated delay for 5 paths.
  4. Analyse errors from input slope, unequal rise and fall, and wire load. Gate: each large error explained.
  5. Package the tool with a short guide and examples.

Tools and resources

ngspice, sky130 PDK, Python. CPU only.

Measurable evaluation

  • Baseline: Unit-sized gates, or a fanout-of-4 rule of thumb.
  • Measure: Predicted vs simulated path delay, extracted g and p, error per path.
  • Success looks like: A calibrated tool with documented error bounds for sky130. Simulation only.

Report each number as measured, simulated, analytical estimate or design target. Nothing here is a pre-measured result.

Final deliverables

Tool, characterisation data, netlists, report.

Career value

Competencies: Logical effort, gate characterisation, SPICE automation.

Resume bullet (use only after you build it and fill in measured numbers): Calibrated logical effort for sky130 and built a path-sizing tool whose predictions were within X percent of ngspice on 5 paths (report your numbers).

Likely interview questions:

  • What is the electrical effort of a path?
  • Why is the optimum stage effort close to 4?
  • How does branching affect sizing?
  • Where does logical effort break down?

Risks and fallback

Rise/fall asymmetry complicates extraction; average them first. Fallback: inverter chains and NAND2 only.

Extensions

  • Compare with Yosys/ABC gate sizing on the same paths
  • Add wire load from the Elmore calculator of MVE333DC-P1

MVE341EC-P36T SRAM Bitcell and Sense Amplifier in sky130: Read/Write Margins and Monte-Carlo Yield Track AAdvancedStretch 5-7 wk25/30

Identification

CMOS Digital VLSI Design (MVE341EC), Semester 4. Level: Advanced / research. Primary track A; secondary: C. Estimated effort: 5-7 weeks (about 60-84 focused hours at roughly 12 h/week). New for the 2026 scheme.

Syllabus mapping: Week 8: memory design; Weeks 5-7: sequential logic and clocking (sense-amplifier timing); Weeks 1-2: device models

Engineering problem

On-chip SRAM dominates accelerator area and much of its energy. The bitcell must read without flipping and write reliably under variation, and those margins shrink at low voltage.

Proposed solution and architecture

Design a 6T bitcell, a small column with precharge and a latch-type sense amplifier in sky130. Measure hold and read static noise margin (butterfly curves), write margin, read current and access time vs supply voltage. Run Monte-Carlo on threshold mismatch to estimate the failure probability per cell, and relate it to the yield of an accelerator scratchpad of a given size.

6T bitcell→Butterfly SNM analysis→Write-margin test→Column with precharge→Latch sense amplifier→Monte-Carlo yield

Implementation plan

  1. Study: 6T operation, read stability and writability (Weste and Harris, memory chapter). Gate: sizing rationale (cell and pull-up ratios).
  2. Build the bitcell and extract hold and read SNM from butterfly curves. Gate: method checked on a textbook example.
  3. Measure write margin and read current vs VDD. Gate: curves from 1.8 V down to the failure point.
  4. Build a 16-cell column with precharge and a latch sense amplifier; measure access time and sense-amplifier offset. Gate: correct reads at the nominal corner.
  5. Monte-Carlo (500 or more samples on the cell): estimate failure probability and, with a Gaussian tail fit, the yield of a 64 KB array; state the extrapolation risk.

Tools and resources

ngspice, xschem, sky130 PDK with mismatch models, Python. CPU only; batch the Monte-Carlo runs.

Measurable evaluation

  • Baseline: Minimum-size cell with equal pull-down and access transistors.
  • Measure: Hold and read SNM, write margin, read current, access time, failure probability, extrapolated array yield.
  • Success looks like: Margins and failure estimates with clear statistical caveats. Simulation only; foundry SRAM cells use special rules not available here.
